# RimProbe protocol v1

Only the local IPv4 loopback interface is bound. Each isolated game process receives a random session ID and a 256-bit token through its environment. The Agent writes `bridge.json` atomically, containing protocol, session ID, PID, port, and Agent version, but never the token. The controller verifies process identity before connecting. This is local process coordination, not a security sandbox for untrusted Mods or other software running as the same user.

Transport: one UTF-8 JSON object per connection, terminated by LF; maximum request and response size is 65,536 bytes including framing. The Agent allows one active network client at a time, a small listen backlog and a bounded main-thread queue. Network read and main-thread waits are bounded. The token is not placed on the command line, in the descriptor, or in run manifests.

Request:

```json
{"protocol":1,"id":"unique-request-id","session_id":"session-id","token":"session-secret","command":"get_state"}
```

Success:

```json
{"protocol":1,"id":"unique-request-id","session_id":"session-id","ok":true,"result":{"phase":"playing","map_ready":true,"long_event_pending":false,"tick":42,"paused":false,"game_version":"1.7.example","map":{"id":0,"width":250,"height":250},"loaded_mods":["ludeon.rimworld"]},"error":null}
```

The version above is an illustrative placeholder, not a validated game version. A real response carries the game's own version string.

Failure:

```json
{"protocol":1,"id":"unique-request-id","session_id":"session-id","ok":false,"result":null,"error":{"code":"main_thread_timeout","message":"Game main thread did not service the request in time."}}
```

Malformed requests that cannot be deserialized may return `invalid_request` with an empty request ID, or the connection may close. Clients must reject uncorrelated responses. Unknown commands return `unknown_command`; arbitrary C# execution is intentionally unavailable.

Commands are `get_state`, `start_building_suite`, `start_contract`, and `cancel_suite`. All responses use a state snapshot with an optional `suite` field. Building start accepts typed `parameters`: `run_id` (32 hex GUID), `def_name`, optional `stuff_name`, `max_ticks` (60..120000), `timeout_seconds` (5..600). Contract start accepts a typed `parameters.contract` (schema=1, recipe=scenario/building_power/ability_cast/item_ingest/ui_info_card) alongside the same run_id/budgets. See composable-plans.md for scenario steps and code-driven-testing.md for recipe observers. Repeating the same run_id does not repeat fixture mutation. Only one running suite across recipe types is permitted; unknown commands never execute code. A task response is not a passing assertion: inspect suite.status, checks and excluded coverage.

Network processing never reads game objects. It enqueues work; a Harmony postfix on `Verse.Root.Update` services up to four pending requests per frame and pumps the bounded building state machine on the main thread. Expired queued requests are cancelled and must not execute later. Already-started actions are not transactional rollbacks: inspect the same run_id after a transport timeout rather than submitting a new one. The network thread does not log through Verse APIs. During long events, snapshots avoid partially initialized maps and scenario actions wait; wall-clock budgets still apply.

Default MCP tools are doctor, capabilities, inspect_mod, run_plan, run_suite, run_contract, get_run, cancel_run and get_artifact. High-level run_plan/run_suite/run_contract launches an owned private-desktop worker, scans startup logs, starts the recipe, polls internally, writes artifacts and terminates the worker. It returns promptly with a run_id; get_run returns stored compact progress. Contract parameters have a nested JSON Schema generated by the installed MCP SDK. `--advanced-tools` adds five low-level launch/get_state/wait_ready/read_logs/stop controls. Mixing low-level lifecycle calls with an active high-level run is unsupported. Ability effects have explicit bounded observers; UI supports real information-card Stats drawing/lifecycle/bounds; ingestion supports normal Ingest and effect observers. The scenario executor composes normal cast/ingest/equip/move/build, typed state discovery and numeric delta assertions; see composable-plans.md. Other custom item interactions, custom UI and pixel/input hit-testing remain unsupported.

Snapshots include red_error_sequence and the latest 16 red_errors (each capped at 1000 characters), from an observational Log.Error(string) postfix. The controller checkpoints before actions, accumulates new entries across polls, and refuses an overall pass when sequence gaps indicate incomplete journal coverage. Duplicate-packageId messages alone are accepted noise and retained separately; other new errors veto a pass. This journal and a bounded file scan are not complete event attribution, nor proof that every error path uses Verse.Log.Error.

Profiles default to inherit enabled Mods/DLC in order from a read-only ModsConfig. Only a disposable profile receives explicit additions. Actual order must match before actions. profile-plan.json and loaded-mods.json document provenance/order; stop.json and terminal reports repeat the actual list and source hash audit. Minimal profiles require explicit selection; source changes are reported, never restored over concurrent user changes.

Artifact names are allowlisted, never arbitrary paths. Overall status may be inconclusive even when suite.status is passed, due to startup errors or incomplete log evidence. Poll until cleanup_complete before starting another run. No baseline attribution is claimed.


## Extended adapters and bounded waiting

Building options include supply_delay_ticks=0..3600, strictly below max_ticks. Nonzero delay temporarily forbids existing eligible material stacks in the disposable map, verifies no delivery/work, then places ground supply for real hauling/construction. Restores originally permitted stacks at finish; it does not delete resources or fill frames directly.

item_ingest creates one fixture Pawn and one item, initializes food only as a declared precondition, issues a normal Ingest job and observes actual Thing.Ingested completion. A stable issued job loadID is used because game Job objects are pooled. ui_info_card opens the actual Stats window and observes genuine Repaint calls, actual logical bounds and normal closure, without system input or manual rendering calls. Unknown semantics remain excluded.

get_run accepts wait_seconds=0..15 (default 0); 10 is recommended with a tool timeout above that bound. Waiting occurs outside the runner lock, returns early after cleanup, and never adds game requests. Stop reports contain cumulative owned-process CPU and memory counters, with memory sample time and explicit unavailable/error fields. These are not Agent-only or foreground-game performance measurements.

Simulation uses a disposable 1280x800 profile; information cards use 1600x1000, UI scale 1. Actual game logical bounds, not configured physical pixels, decide bounds assertions. Player Prefs remain untouched.
